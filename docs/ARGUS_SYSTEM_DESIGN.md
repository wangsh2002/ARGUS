## 1. 文档目的

本文档用于统一 ARGUS 的产品目标、前端信息架构、后端算法流程、图谱本体、数据库结构和工程边界。它既描述当前比赛版本已经形成的能力，也记录后端尚未完全产品化但已经确定的实现思路。

本文档不把设计目标包装成现状。所有能力分为三种状态：

- **已实现：** 当前代码和数据库中已经存在，并可通过前端或接口验证；
- **部分实现：** 已有主要流程或数据结构，但算法质量、数据覆盖或交互闭环仍需完善；
- **设计确定：** 产品和技术方向已经确定，比赛版可以演示，尚未完成生产级工程化。

## 2. 产品定位

ARGUS 是面向 **SOC 二线分析员** 和 **应急响应人员** 的 APT 技战术数据服务平台。平台不以“查到一个 IOC 是否恶意”为终点，而是从不完整的告警、威胁情报、文件或自然语言线索出发，帮助分析人员完成：

1. 识别输入中的 IOC、漏洞、工具、恶意软件、行为和 ATT&CK 技术；
2. 判断这些线索属于一个还是多个攻击活动；
3. 在历史情报中寻找可解释的攻击路径；
4. 对缺失步骤进行受约束补全，并预测可能的后续行为；
5. 展示每个节点、每条边和每项判断的来源证据；
6. 生成可阅读、可导出的调查与处置建议；
7. 在页面末端提供辅助归因及其支持、反证和不确定性。

平台的核心展示价值不是“给出某个组织名称”，而是：

> 将碎片线索还原为可核验的攻击过程，并告诉安全人员已经发生了什么、缺少什么、接下来可能发生什么、为什么这样判断、应该优先核查和处置什么。

组织归因仍是算法能力之一，但不是页面首要叙事。归因放在完整路径、证据和处置建议之后，避免产品被误解为只能进行低可靠度的“猜组织”。

## 3. 核心用户与任务

### 3.1 SOC 二线分析员

SOC 二线分析员承接一线告警，需要在有限时间内判断告警是否值得升级。他们关注：

- 多条孤立告警是否属于同一攻击活动；
- 当前观测位于攻击过程的哪个阶段；
- 哪些节点是直接观测，哪些是历史补全；
- 是否存在尚未被当前检测覆盖的关键步骤；
- 下一步最可能出现什么行为，应补查哪些日志和资产；
- 每个结论是否可以回到真实报告和原文证据。

### 3.2 应急响应人员

应急响应人员关注受影响范围、攻击过程和处置优先级。他们需要：

- 从邮件、终端、网络和边界设备线索中还原完整过程；
- 识别分支、替代路径和汇合点，而不是只看一条直线；
- 找到与每个攻击步骤相关的 IOC、工具、漏洞和资产；
- 判断攻击者可能已经完成的动作与尚待验证的动作；
- 获得按 P0/P1/P2 分级的核查、遏制、恢复和持续监测建议；
- 导出包含来源和证据链的报告。

## 4. 产品原则

### 4.1 证据优先

每一个重要判断都必须能够回答“依据是什么”。节点和边分别绑定证据，不能使用两个节点各自存在于报告中来间接证明二者之间存在关系。

### 4.2 事实状态严格区分

系统必须区分：

- `observed`：输入或来源直接观测；
- `reconstructed`：依据历史路径和图约束补全；
- `predicted`：位于最后直接观测之后的后续行为预测；
- `candidate`：尚待复核的实体、关系或活动合并候选；
- `refuted`：存在明确反证或已被分析员拒绝。

高置信度预测仍然不是事实。

### 4.3 攻击过程不是一条直线

真实攻击活动可能包含：

- 多种初始入口；
- 不同载荷或投递变体；
- 条件成功/失败分支；
- 并行动作；
- 多路汇合；
- 与主过程有关但不属于主干的实现细节、IOC、工具和资产。

因此底层采用有向属性多重图，前端只生成“主干 + 树状支线 + 阶段泳道”的任务型投影。

### 4.4 在线查询与历史知识入库分离

在线查询用于快速研判，读取历史图谱但不直接污染历史知识。高保真入库通过独立流程完成：

1. 保存来源原文；
2. 生成抽取和图谱增量预览；
3. 通过质量门；
4. 对待定片段进行复核；
5. 显式发布知识版本；
6. 必要时回滚。

### 4.5 克制展示

前端只展示能帮助用户做判断的内容。图谱不是装饰，指标不是越多越好。每个模块必须回答一个明确问题：

- 发生了什么；
- 依据是什么；
- 缺失了什么；
- 下一步可能是什么；
- 应该做什么。

## 5. 总体架构

ARGUS 采用浏览器前端、同源 API、Python 算法服务和关系数据库的分层结构。

```text
桌面 Web 前端
  ├─ 综合查询 / IOC 结果
  ├─ 攻击活动候选与路径研判
  ├─ 情报关系探索
  ├─ 攻击组织目录与画像
  ├─ 情报入库与路径复核
  └─ ARGUS GPT
          │
          ▼
同源 Web API（隐藏密钥、统一错误和数据契约）
          │
          ▼
Python FastAPI 算法服务
  ├─ 来源归档与证据定位
  ├─ 活动分段
  ├─ 分块并行事件图抽取
  ├─ 实体规范化与消歧
  ├─ 路径组装、主干投影与质量门
  ├─ 在线补全、预测、归因与处置生成
  └─ 入库版本、复核与回滚
          │
          ▼
SQLite（比赛版唯一事实源）
  ├─ 原始来源与证据片段
  ├─ 规范实体与关系
  ├─ 活动事实图与历史路径
  ├─ 分析运行与展示投影
  ├─ 复核记录与知识版本
  └─ 归因、响应规则与审计日志
```

比赛版本优先保证单机可运行、数据可复现、演示稳定和证据可追踪。生产化时建议迁移到 PostgreSQL + pgvector + 对象存储；只有在多跳查询成为明确瓶颈后再增加 Neo4j 或其他图投影，不在早期双写两套主数据库。

## 6. 前端设计

### 6.1 全局信息架构

当前主导航统一为：

1. **综合查询**：统一搜索入口和历史研判报告；
2. **攻击组织**：组织目录和组织画像；
3. **情报图谱**：围绕真实实体进行跨报告关系探索；
4. **情报入库**：高保真来源解析、预览、质量门和发布；
5. **路径复核**：只展示待分析员确认的 AttackFlow 暂存候选；
6. **ARGUS GPT**：在当前证据上下文中进行辅助问答。

所有页面使用统一的 ARGUS 顶部导航、浅灰蓝背景、白色内容面和红色选中/风险强调。桌面端是唯一需要精确适配的目标。

### 6.2 全局导航与返回

前端维护页面状态栈。进入实体、报告、攻击路径、组织画像或图谱后，返回操作应回到真实的上一级页面，而不是无条件回到首页。主导航点击属于重新选择一级模块，会清空不必要的嵌套上下文。

### 6.3 综合查询首页

首页承担“开始一次研判”和“继续一次历史研判”两个任务。

首屏包含：

- 平台标题与一句价值说明；
- 统一搜索栏；
- 输入聚焦后展开的搜索类型、推荐搜索和历史查询；
- 查询按钮。

下方直接展示历史研判报告，不再设置独立历史报告列表页。报告卡片可以点击进入已有分析结果。

搜索支持：

- IP、域名、URL、Hash；
- CVE；
- 攻击组织；
- 恶意软件与工具；
- 报告标题和关键词；
- 自然语言威胁情报或告警；
- 攻击路径研判。

推荐搜索优先放置数据完整、页面效果稳定、证据丰富的真实案例，避免用户点进空页面或低质量图谱。

### 6.4 IOC / 实体查询结果

IOC 是独立情报对象，图谱是优势但不应压过 IOC 本身。结果页采用连续单页结构，不使用“情报概览、来源证据、历史报告、关联攻击链”标签页切换。

推荐阅读顺序：

1. **风险结论与基础属性**：类型、规范值、首次/最后出现、来源数；
2. **情报洞察**：恶意判断、相关行为和已知上下文；
3. **来源证据**：短引文、发布机构、时间、原始链接；
4. **历史报告**：包含该实体的报告及其上下文；
5. **关联攻击链**：该 IOC 参与的具体攻击步骤；
6. **弱化图谱**：只展示有限一跳关系，可进入完整情报图谱。

### 6.5 攻击活动候选页

当输入是一整份报告、告警或多条自然语言线索时，系统不应直接假设只有一条攻击链。预处理后先展示一个或多个攻击活动簇。

每个活动簇展示：

- 活动名称和范围；
- 命中的直接观测；
- 识别出的主过程摘要；
- 节点数、关系数、分支数；
- 未归属线索；
- 与其他簇可能属于同一活动的待定关系；
- 来源覆盖和质量状态。

用户可以：

- 选择一个活动进入路径研判；
- 微调节点名称和类型；
- 调整错误的活动归属；
- 接受或拒绝待定缺边；
- 保持多个活动分开。

活动簇不是为了强制“一个报告一条链”。报告可以产生 0、1 或多个活动；跨报告也可以支持同一活动。

### 6.6 攻击路径研判页

这是平台核心演示页面。页面按安全人员的决策顺序组织。

#### 6.6.1 顶部系统研判

展示：

- 当前确认推进到的攻击阶段；
- 直接观测数量；
- 补全步骤数量；
- 预测行为数量；
- 首要行动建议。

这些数字必须来自当前选中活动和投影，不能因为前端状态未初始化而显示为 0。

#### 6.6.2 攻击阶段判定

将主路径步骤按阶段横向排列，使用明确图例区分：

- 红色实线或实心节点：直接观测；
- 橙色或虚线：系统补全；
- 蓝灰色虚线：预测下一步。

阶段条与主图联动。点击阶段可定位图谱节点和右侧证据。

#### 6.6.3 关联知识图谱

主路径从左到右排列。其他信息从对应行为节点向外树状或放射状延伸：

- IOC / 基础设施；
- 恶意软件与工具；
- 漏洞；
- 资产；
- ATT&CK 技术；
- 来源证据；
- 并行分支、替代路径和汇合关系。

点击节点后：

- 右侧显示概览、证据和关联；
- 可逐跳展开一层；
- 可一次展开当前节点全部直接关系；
- 可撤销最近一次展开；
- 节点位置保持稳定，避免点击后整图跳动；
- 拖动画布时禁止浏览器文本选中导致整页变蓝。

#### 6.6.4 攻击阶段泳道

泳道是图谱的稳定阅读视图，与上方真实图谱联动。它按阶段或任务分组展示主干和关键分支，用于在节点很多时快速理解攻击过程。

泳道支持折叠。折叠后保留阶段名称、关键结论和节点计数；展开后显示相关行为、状态和对应证据。

#### 6.6.5 处置响应方案

按 P0、P1、P2 组织：

- **P0 立即核查与遏制**：当前高风险资产、CVE、凭据、C2 和关键日志；
- **P1 范围确认与清除**：同源 IOC、横向扩散、持久化、受影响账户与主机；
- **P2 恢复与持续监测**：补充检测、回归验证、监测后续预测行为。

建议只能阅读和导出，不在比赛版执行自动封禁、隔离或配置变更。建议必须标明依据、适用条件和对应的路径节点。

#### 6.6.6 归因分析与可解释链路

归因放在页面末端但不能草率。应展示：

- 候选组织排序；
- 工具、TTP、有序路径、基础设施、目标行业和历史活动的支持证据；
- 来源可靠性；
- 时间衰减；
- 反证与冲突；
- 结论口径和不确定性。

点击某条归因路径可打开真实组织知识图谱，并高亮当前案例命中的可解释路径。归因只辅助研判，不替代攻击过程和处置建议。

### 6.7 情报图谱

情报图谱不是默认铺满一张固定示例图，而是一个从真实实体开始的关系探索入口。

首页与综合查询保持统一的全局导航、标题区和搜索栏位置。搜索内容针对图谱场景，支持 IOC、漏洞、工具、组织、ATT&CK 技术和报告。

进入实体后：

- 左侧按实体类型、关系类型和证据范围筛选；
- 中间显示稳定的放射拓扑；
- 右侧显示当前节点或关系的概览、来源和直接关联；
- 节点角标提示尚未展开的邻居数量；
- 支持逐跳展开、全部展开、撤销和回到初始范围；
- 只降低筛选外节点的视觉权重，不改变节点位置；
- 关系本身可被点击并审计来源。

情报图谱用于发现关联和验证来源，不强制主路径。攻击路径研判页才使用固定主干投影。

### 6.8 攻击组织目录与画像

组织目录用于从整体概述进入单个组织画像。目录卡片展示：

- 规范组织名和别名；
- 活跃时间；
- 主要目标行业；
- 相关工具、TTP、历史活动和来源数量；
- 数据更新时间和可信来源等级。

组织画像由数据库实时聚合，而不是写死数字。新增组织、攻击链、IOC 或关系后，重新查询即可更新统计。后端不可用时可以显示最近一次本地快照，但必须明确离线状态。

组织画像包括：

- 基本信息和公开归因；
- 常用工具与恶意软件；
- ATT&CK 技战术分布；
- 历史活动时间线；
- 目标行业；
- 关联 IOC；
- 组织知识图谱；
- 相关报告和来源。

### 6.9 情报入库

情报入库服务于历史知识沉淀，要求比在线查询更保真。

用户输入原始报告、官方链接、告警或文件后，页面依次展示：

1. 来源元数据和原文哈希；
2. 文档解析状态；
3. 实体规范化与合并候选；
4. 攻击活动分段；
5. 局部事件图与全局组装结果；
6. 新增实体、关系、活动和证据数量；
7. 质量门结果；
8. 待复核片段；
9. 发布知识版本。

纯 IOC 报告、组织背景或能力说明可以合法入库为 `no-path`，不能为了让页面好看而生成虚假攻击链。

### 6.10 路径复核

复核中心只展示待审核片段，而不是把整份报告重新交给分析员阅读。复核单位可以是：

- 缺失关系候选；
- 分支或汇合候选；
- 活动簇合并候选；
- 模糊实体归并；
- 主干选择冲突；
- 无法稳定归属的行为片段。

分析员可接受、修改或拒绝，并填写简短理由。决策进入审计记录，修改后的结果用于发布知识版本。

### 6.11 ARGUS GPT

GPT 接收当前案件的实体、路径步骤、来源片段和算法状态，用于：

- 解释为什么某一步被补全；
- 比较两个候选活动；
- 总结来源一致点和冲突点；
- 将规则生成的处置建议改写成当前案例语言；
- 辅助组织支持与反证总结。

GPT 不允许：

- 生成不存在的来源；
- 自动确认节点或关系；
- 直接写入历史图谱；
- 发明补丁版本、IOC 或执行命令；
- 自动执行处置。

## 7. 前端数据与状态设计

前端使用统一 `Snapshot` 作为本地知识快照，包含实体、关系、证据、报告、组织画像、处置规则、算法配置、来源原件、历史路径和分析投影。

页面状态至少包括：

- 当前页面；
- 查询文本和已提交文本；
- 查询模式；
- 选中的报告、攻击活动、组织和图谱根实体；
- 后端路径分析结果；
- 加载、就绪和离线状态；
- 页面历史栈。

前端数据原则：

- 后端连接成功时优先使用真实接口；
- 不再混用未标识的演示数据；
- 如果必须使用本地快照，应明确它是同步自 SQLite 的同源快照；
- 页面不得根据缺失字段擅自伪造数量或关系；
- 图谱布局状态与知识事实分离。

## 8. 后端总体设计

### 8.1 服务边界

后端分为两条业务链：

#### 在线研判链

- 归档输入；
- 抽取可验证观测；
- 识别攻击活动候选；
- 匹配历史活动图；
- 补全缺失步骤；
- 预测后续行为；
- 生成证据、评分和建议；
- 保存冻结的分析快照；
- 不写历史知识图谱。

#### 高保真入库链

- 保存原始来源；
- 活动分段；
- 分块并行抽取局部事件图；
- 稀疏组装完整活动图；
- 实体规范化和消歧；
- 生成主干与分支投影；
- 运行质量门；
- 对问题片段进行针对性返修；
- 进入人工/代理复核；
- 显式发布知识版本；
- 支持回滚。

### 8.2 来源归档与解析

每份来源必须保存：

- 发布机构和原始 URL；
- 发布时间和采集时间；
- SHA-256；
- MIME 类型；
- 许可与 TLP；
- 原始文件或可验证副本路径；
- 解析器名称和版本；
- 原文证据位置；
- 审核状态。

来源按内容哈希去重。同一内容再次提交时复用已有来源和证据锚点。

PDF、HTML、文本、JSON 和告警输入先转换为可定位文本。证据片段保存页码、段落、行号、字符范围、JSON Path 或表格位置。解析不能只保存一大段全文而失去定位能力。

### 8.3 攻击活动分段

抽取前先判断报告中存在几个独立攻击活动。分段依据包括：

- 攻击主体或恶意软件；
- 时间窗口；
- 目标或受害范围；
- 样本和基础设施；
- 明确的章节和上下文指代；
- 完整的投递、执行和后渗透过程。

背景、归因讨论、纯 IOC 附录、检测规则、图注和产品介绍不作为攻击步骤。

同一活动中的多种投递入口或载荷变体可以形成分支；不同攻击组织、时间批次或互不相连的案例应分开。无法确定时形成待复核活动，而不是强行混入其他簇。

### 8.4 分块并行事件图抽取

长报告按活动边界和结构切片。每个切片并行调用受 JSON Schema 约束的大模型，抽取局部事件图：

- 原子攻击行为；
- 行为之间的因果或效果依赖；
- 分支与汇合；
- 行为相关的工具、IOC、漏洞、资产和 ATT&CK 技术；
- 每个节点和边的证据行号；
- 模态、否定和置信度。

默认并发受限，避免 API 瞬时过载。结果按来源哈希、模型和提示词版本缓存。

局部图组装为全局图时只连接有证据或强约束支持的关系。共享组织、工具、时间或基础设施只能形成跨活动关联候选，不能自动成为因果边。

### 8.5 节点设计

攻击路径中的主节点必须是简短、可识别的原子行为，例如：

- “发送 NATO 主题钓鱼邮件”；
- “用户打开 LNK”；
- “PowerShell 下载载荷”；
- “Jaguar Tooth 建立未认证访问”；
- “收集 CLI 设备信息”。

不允许将一整句分析结论、报告标题或长段描述直接作为节点。长文本进入节点描述或证据片段。

节点应包含：

- 简短标签；
- 行为类型；
- ATT&CK tactic / technique 映射；
- 时间和资产范围；
- 事实状态；
- 置信度；
- 证据引用；
- 相关上下文实体；
- 审核状态。

### 8.6 实体规范化与消歧

确定性规则优先处理强类型实体：

- IPv4 / IPv6；
- 域名；
- URL 和网络端点；
- 邮箱；
- MD5 / SHA-1 / SHA-256；
- CVE；
- ATT&CK 技术编号。

规则负责 refang、大小写、默认端口、IDNA、哈希算法和稳定 `canonical_key`。同一 IOC 的不同写法合并到同一规范实体，但每次来源出现仍保留独立 `entity_mention` 和证据。

恶意软件、工具和组织采用：

1. external ID 和规范别名精确命中；
2. 名称与别名候选召回；
3. 向量语义、邻域、时间和来源联合打分；
4. 阈值拒识；
5. 模糊结果进入待复核。

仅凭名称相似不得自动合并。攻击行为实例不跨活动合并；跨报告对齐的是行为语义和实体身份，不是直接把两次具体行为变成同一个节点。

### 8.7 活动事实图与主干投影

后端先抽取尽可能完整的活动事实图，再由确定性模块选择主干。这样可以保留分支和细节，同时允许更换展示投影而不必重抽报告。

主干不是最长路径。主干应优先满足：

- 属于同一活动；
- 因果或效果依赖连续；
- 覆盖关键安全状态变化；
- 符合真实攻击过程；
- 证据充分；
- 避免将实现细节、重复动作和纯 IOC 当作主干；
- 在多个入口或分支中选择最能解释当前研判目标的核心路径。

系统支持 `soc-triage` 和 `incident-response` 两种投影：

- SOC 投影更强调命中观测、检测缺口和下一步风险；
- 应急响应投影更强调完整过程、受影响资产、分支和处置。

投影保存主干节点、主干依赖、分支组、泳道位置、关键上下文和选择理由。投影是可重新计算的展示结果，不复制底层事实。

### 8.8 路径补全

补全流程不是让大模型自由续写。候选来自：

- 同一历史活动中已复核的前后继关系；
- 多份报告中对齐后的 Attack Flow 模式；
- ATT&CK procedure 和工具前置条件；
- 技术共现与转移统计；
- 当前资产、平台、时间和攻击阶段。

候选经过约束过滤：

- 时间不能明显逆序；
- 平台和资产必须兼容；
- 前后安全状态必须连续；
- 不跨越不相关攻击活动；
- 必须能够给出历史路径或知识依据；
- 存在反证时降低分数或拒绝。

输出包括候选步骤、插入位置、评分分解、证据路径和需要补查的观测。

### 8.9 下一步预测

预测位于最后一个直接观测之后，使用：

- 历史 Attack Flow 后继；
- ATT&CK 技术共现/转移矩阵；
- 工具、平台和资产前置条件；
- 当前攻击阶段；
- 已观测分支。

预测输出 Top-K，不包装成确定事实。每个预测同时给出：

- 为什么会发生；
- 哪些历史路径支持；
- 哪些日志、事件或资产可以验证；
- 预测失效的条件。

### 8.10 组织归因

归因是次要任务，使用多证据加权而不是单 IOC 命中。评分建议拆分为：

- 特定恶意软件和工具重合；
- ATT&CK 技术组合；
- 有序路径相似；
- 基础设施复用和时间衰减；
- 目标行业和地区兼容；
- 来源可靠性；
- 反证扣分。

输出候选排序、支持和反证，不输出伪精确概率。大模型只负责汇总解释，不负责决定排序。

### 8.11 处置建议

处置建议先由规则和权威知识生成：

- CVE → 厂商公告、CISA KEV、受影响产品和修复核查；
- ATT&CK 技术 → 数据源、检测和缓解措施；
- IOC → 日志回溯、同源排查和时间范围；
- 资产 → 隔离前置条件、凭据和恢复步骤；
- 预测行为 → 待验证信号和补充监测。

大模型只做去重、排序和案例化改写。最终建议保持可读和可导出，不自动执行。

### 8.12 质量门与针对性返修

质量门按问题类型判断：

- 来源证据是否可定位；
- 节点是否为原子行为；
- 边是否有自己的证据；
- 是否存在无证据跨活动连接；
- 图是否存在非法环或不合理逆序；
- 分支和汇合是否正确；
- 实体是否可规范化；
- 主干是否连续且符合攻击过程；
- 是否错误地把纯 IOC 报告强制生成路径。

当某一项失败时，只将问题片段、相关证据和错误原因注入修复提示词，让模型专注修复该局部问题。修复后重新运行确定性校验。一次返修仍无法通过的片段进入复核中心，不无限循环。

## 9. 传统算法与 AI 的分工

| 任务 | 确定性算法 / 图算法 | 大模型 |
|---|---|---|
| 文档归档 | 哈希、MIME、URL、解析版本、证据定位 | 修复破碎文本、识别结构 |
| 强类型实体 | 正则、refang、校验、规范键 | 识别不规则上下文提及 |
| 活动分段 | 时间、章节、共享锚点和冲突约束 | 理解叙事归属并提出活动簇 |
| 事件图抽取 | Schema 校验、类型白名单、证据行验证 | 从自然语言抽取行为、关系、分支 |
| 实体消歧 | external ID、别名、向量/邻域评分、阈值 | 对 Top-K 候选给出语义解释 |
| 局部图组装 | DAG、时间、资产、平台和活动边界约束 | 仅提出缺边候选 |
| 主干选择 | 图约束、状态变化、证据覆盖和任务投影 | 不负责最终主干裁决 |
| 路径补全 | 子图检索、K 路径、约束过滤、评分 | 解释候选和验证缺口 |
| 下一步预测 | 转移矩阵、历史后继、校准 | 将统计依据写成研判语言 |
| 归因 | 多证据加权、时间衰减、反证扣分 | 汇总支持与反证 |
| 处置 | 规则映射权威模板 | 去重和案例化改写 |
| 审计 | 版本、哈希、证据和快照 | 不拥有最终裁决权 |

总原则：

> 大模型负责阅读、提议和解释；确定性代码、统计模型和图算法负责校验、排序、约束和留痕。

## 10. 本体与标准

ARGUS 不把 STIX、ATT&CK 和 Attack Flow 视为三选一。

### 10.1 STIX 2.1

用于通用 CTI 语义和交换：

- `intrusion-set`：攻击组织；
- `campaign`：已命名活动；
- `malware` / `tool`；
- `vulnerability`；
- `attack-pattern`；
- `indicator` 与 SCO；
- `report`；
- `course-of-action`；
- Relationship、Sighting、外部引用和版本。

STIX 是交换语义，不直接作为数据库物理表。

### 10.2 MITRE ATT&CK

用于行为词表、泳道分类和跨报告语义对齐。行为实例映射到 ATT&CK technique / sub-technique，但技术类型不能替代本次活动中的具体行为节点。ATT&CK tactic 不代表严格时间顺序。

### 10.3 Attack Flow

用于表达一次攻击活动中的：

- Attack Action；
- Asset；
- Condition；
- AND / OR；
- Effect；
- 分支和汇合。

ARGUS 内部活动事实图与 Attack Flow 兼容，并增加证据断言、事实状态、审核状态和展示投影。

### 10.4 CACAO 子集

用于只读处置方案和导出：

- Investigation；
- Detection；
- Mitigation；
- Remediation；
- 条件、目标和步骤说明。

比赛版不执行 CACAO 动作。

### 10.5 MISP 兼容

MISP 用于 Event、Attribute、Object、Galaxy、TLP 和社区 Feed 的导入导出。MISP correlation 只产生关联候选，不能直接作为攻击路径因果边。

## 11. 逻辑数据模型

### 11.1 来源证据层

#### `SourceArtifact`

保存原始文件或可验证副本的来源、许可证、TLP、哈希和存储路径。

#### `SourceDocument`

保存可解析文档的标题、发布机构、原始 URL、发布时间、正文和审核状态。

#### `SourceSpan`

保存页码、段落、行号、字符范围、选择器、短引文哈希和解析器版本。

### 11.2 规范知识层

#### `CanonicalEntity`

保存规范实体身份：

- entity type；
- label；
- canonical key；
- normalized value；
- aliases；
- external IDs；
- first / last seen；
- properties；
- review state。

#### `EntityMention`

保存某个来源中对规范实体的一次具体提及，包括原始写法、规范值、证据片段、入库运行和置信度。

#### `KnowledgeRelationship`

保存可复用知识关系，例如 `uses`、`targets`、`exploits`、`communicates-with`、`resolves-to`。知识关系不等于攻击过程依赖。

### 11.3 活动事实与攻击流层

#### `ActivityPath`

保存一个历史活动或已确认路径的边界、时间、受害范围、主来源和审核状态。

#### `ActivityPathNode`

保存活动中的行为实例。节点标签必须是原子行为，`assertion_origin` 区分来源观测、人工确认、算法补全和算法预测。

#### `ActivityPathEdge`

保存 `sequence`、`enables`、`causes`、`conditional`、`branch` 和 `merge`，支持 `branch_group` 和 `condition_label`。

#### `ActionContextLink`

将 IOC、工具、漏洞、资产、技术等上下文实体挂到具体行为节点，带角色和方向，例如：

- `delivers-payload`；
- `uses-tool`；
- `connects-to`；
- `exploits-vulnerability`；
- `on-asset`；
- `mapped-to-technique`。

IOC 不直接排成攻击主干，而是挂到使用它的具体动作。

#### `PathEvidenceLink`

将节点或边连接到独立证据片段，区分：

- supports / contradicts / context；
- direct / corroborating / background；
- 机器提议、代理复核、人工确认和拒绝。

### 11.4 分析与投影层

#### `PathAnalysisRun`

冻结一次在线研判的输入、算法版本、知识快照和完整结果。

#### `AnalysisProjection`

保存 SOC 或应急响应视角下的主干、分支组、泳道和节点状态。

#### `AttributionRun`

保存候选组织、各分项得分、支持、反证和最终排序。

#### `ResponseRule`

保存实体、事件或阶段到 P0/P1/P2 处置模板的映射。

### 11.5 入库、审核与版本层

#### `KnowledgeIngestionRun`

保存暂存结果、质量门、图谱增量和路径结果。

#### `ReviewRecord`

记录接受、修改、拒绝、审核人、理由、前后状态和时间。

#### `KnowledgeVersion`

记录一次发布产生的增量，支持事务发布和回滚。

#### `AuditLog`

记录重要操作、算法版本和用户动作。

## 12. 当前 SQLite 物理数据库

比赛版使用 `data/argus_cti.db` 作为唯一事实源。现有表可按职责分组：

| 分组 | 主要表 |
|---|---|
| 原始来源 | `raw_reports`, `corpus_collections`, `source_artifacts`, `source_documents`, `source_spans` |
| 规范知识 | `entities`, `aliases`, `entity_mentions`, `relationships`, `evidence` |
| 历史路径 | `activity_paths`, `activity_path_nodes`, `activity_path_edges`, `action_context_links` |
| 路径证据 | `path_evidence_links`, `action_context_evidence_links` |
| 匹配与投影 | `flow_match_runs`, `analysis_projections` |
| 组织与归因 | `actor_profiles`, `attribution_runs`, `attribution_candidates`, `attribution_evidence` |
| 处置 | `response_rules` |
| 入库与版本 | `import_jobs`, `knowledge_ingestion_runs`, `knowledge_versions` |
| 审核与评测 | `review_records`, `gold_evaluation_cases`, `curated_extraction_baselines` |
| 模型与缓存 | `algorithm_configs`, `extraction_cache` |
| 审计 | `audit_log`, `schema_migrations` |

### 12.1 关键约束

- 规范实体通过 `canonical_key` 唯一；
- 来源原件和文档通过 SHA-256 去重；
- 路径节点在同一活动内通过 `occurrence_key` 唯一；
- 路径边在同一路径、同一端点和同一类型下唯一；
- 证据必须绑定节点或边二者之一；
- 路径状态、审核状态和来源状态使用 CHECK 约束；
- 分析运行保存知识快照和算法版本；
- 知识发布和回滚有独立版本记录。

### 12.2 正式存储边界

- 来源原件写入 `source_documents/source_artifacts/source_spans`；
- AttackFlow 候选写入 `knowledge_ingestion_runs`，通过复核后发布到版本化 AttackFlow 表；
- 不构成攻击流的来源只写入规范实体、实体提及与证据关系；
- 在线匹配只读取已发布 AttackFlow，不从通用实体关系反推历史攻击过程；
- 前端通过运行时 API 读取数据，不执行构建期静态快照导出。

### 13.2 建议补充的稳定接口

- `POST /v1/search`：统一实体、报告和组织检索；
- `GET /v1/entities/{id}`：实体详情、来源和一跳关系；
- `GET /v1/entities/{id}/graph`：按类型、关系和跳数返回图谱；
- `GET /v1/activities/{id}`：完整活动事实图；
- `GET /v1/activities/{id}/projection?goal=`：获取指定任务投影；
- `GET /v1/reports/{id}`：报告与分析结果；
- `GET /v1/actors` 和 `GET /v1/actors/{id}`；
- `POST /v1/response-plans`：根据冻结分析生成只读处置方案；
- `POST /v1/exports`：生成 Markdown、JSON、STIX、Attack Flow 或 CACAO 子集。

所有响应应包含：

- `schema_version`；
- `generated_at`；
- `knowledge_snapshot`；
- `algorithm_version`；
- `warnings`；
- 可追踪的实体、关系和证据 ID。

## 14. 数据来源与语料策略

### 14.1 数据来源优先级

第一层：规范和权威结构化数据。

- MITRE ATT&CK STIX；
- CISA KEV；
- NVD；
- FIRST EPSS；
- CWE / CAPEC。

第二层：一手威胁报告。

- CISA / NCSC / CERT；
- Microsoft；
- Cisco Talos；
- ESET；
- Unit 42；
- Mandiant 等。

第三层：IOC 与样本生态。

- ThreatFox；
- MalwareBazaar；
- URLhaus；
- MISP Feed。

### 14.2 论文数据集的使用方式

论文数据集只作为原始报告获取渠道，不使用其结构化标注作为 ARGUS 的直接答案。导入时：

1. 保存数据集版本和许可证；
2. 保存报告原文和 SHA-256；
3. 核验原发布方 URL；
4. 使用 ARGUS 自己的流程重新抽取；
5. 保留数据集记录 ID，但不把其标签当作事实；
6. 对演示案例进行代理辅助复核。

### 14.3 比赛版数据规模

建议保持精而不大：

- 约 50 份真实报告；
- 每个重点真实组织约 3 份报告；
- 20 条左右高质量完整分支路径；
- 5–10 个金标准或回归案例；
- 3 个重点演示案例；
- ATT&CK、Attack Flow 和 TIE 作为背景知识与预测基线。

## 15. 核心演示闭环

推荐使用跨邮件、终端和边界设备的综合情报包作为主案例，并保留 Jaguar Tooth 作为清晰的边界设备案例。

完整演示流程：

1. 用户粘贴自然语言告警或威胁情报；
2. 系统识别多个攻击活动簇，而不是直接生成一条链；
3. 用户查看活动簇命中线索、未归属线索和待定缺边；
4. 选择其中一个活动进入路径研判；
5. 顶部显示直接观测、补全和预测；
6. 图谱显示左到右主干、真实分支和上下文 IOC；
7. 点击补全步骤查看历史来源和精确短引文；
8. 泳道折叠/展开并与图谱联动；
9. 页面下方展示 P0/P1/P2 处置建议；
10. 最后查看候选归因、支持、反证和组织知识图谱；
11. 导出带来源的研判报告；
12. 如需沉淀，转到情报入库，经质量门和复核后发布知识版本。

这个闭环展示的价值是“从碎片告警到可执行调查依据”，不是单纯展示一张图。

## 16. 可靠性、安全与审计

### 16.1 数据可靠性

- 原文 SHA-256 固定；
- 每条证据保存位置和短引文；
- 来源可靠性与判断置信度分开；
- 模型结果缓存并记录模型、提示词和版本；
- 所有分析保存知识快照；
- 无来源结论不得进入已确认状态。

### 16.2 安全

- API 密钥仅服务端保存；
- 原始上传限制大小和 MIME；
- 不自动下载或解压恶意样本；
- URL 抓取设置白名单/隔离和超时；
- 导出内容进行 HTML/Markdown 转义；
- 不执行模型生成的命令；
- 不自动封禁、隔离或修改资产。

### 16.3 审计

记录：

- 来源导入；
- 模型和算法运行；
- 实体合并；
- 节点和边修订；
- 片段接受/拒绝；
- 知识发布和回滚；
- 导出；
- 用户触发的重要页面操作。

## 17. 质量评估

比赛版重点是可用和可信，不必包装成论文级评测，但需要保留基本指标：

- 实体规范化准确性；
- 节点是否为原子行为；
- 节点/边证据覆盖率；
- 活动分段合理性；
- 分支/汇合正确性；
- 主干连续性和攻击过程合理性；
- 补全是否有历史路径依据；
- 预测 Top-K 是否可解释；
- 跨报告合并是否依赖强锚点；
- `no-path` 报告是否被正确处理；
- 页面从查询到证据、建议和导出的闭环是否可运行。

必须设置的硬指标：

- 已确认节点和边 100% 可回到 SourceSpan；
- 未标记的无源结论为 0；
- 长句或报告标题作为攻击步骤节点为 0；
- 不同攻击活动被无证据强连为一条路径为 0。

## 20. 验收标准

一个可接受的比赛版本必须满足：

1. 用户能从首页输入 IOC、自然语言告警或报告；
2. 推荐搜索进入的页面全部有真实可读内容；
3. 多活动输入先展示活动簇；
4. 攻击路径不是固定直线，能够表达分支和上下文；
5. 主干节点是原子行为，IOC 挂到具体行为；
6. 直接观测、补全和预测清楚区分；
7. 点击节点或关系能够看到来源证据；
8. 泳道与图谱联动且可折叠；
9. 处置建议突出、可读、可导出；
10. 归因位于末端但包含支持、反证和可解释路径；
11. 情报图谱和其他页面使用统一外壳；
12. 所有返回操作回到真实上一级；
13. 后端不可用时明确提示，不能静默展示伪造结果；
14. 纯 IOC 或无攻击过程报告可作为 `no-path` 合法入库；
15. 知识入库必须经过质量门、复核和版本发布。

## 21. 术语表

- **IOC：** IP、域名、URL、Hash 等可用于检测和关联的技术线索。
- **APT：** 具备明确目标、长期潜伏和持续技战术演进特征的高级持续性威胁。
- **攻击活动：** 在一定主体、目标、时间和技术上下文中发生的一组相关攻击行为。
- **活动簇：** 系统根据证据暂时聚合的攻击活动候选，可能待复核。
- **行为实例：** 某次攻击中发生的具体原子动作。
- **主干：** 最能解释关键安全状态变化的核心攻击过程，不等于最长路径。
- **支线：** 与主过程相关的替代入口、并行动作、实现细节或补充行为。
- **补全：** 在已观测节点之间依据历史路径和约束恢复缺失步骤。
- **预测：** 在最后直接观测之后给出可能后续行为。
- **SourceSpan：** 可以精确定位到原始来源的最小证据片段。
- **知识快照：** 一次算法运行所使用的冻结实体、关系和版本状态。
- **投影：** 从完整事实图计算出的主干、泳道和展示状态。
